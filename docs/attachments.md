# Event files: capability findings and pending design

Checked 24 October 2026. **File attachments are not implemented or deployed.** This document records source and documentation findings and requirements for a future implementation. It does not add tools, file storage, provider access or authorization. The choice between native calendar attachments and files associated only within this MCP integration remains with the user.

## Current EventKit limitation

The public `EKEvent` and inherited `EKCalendarItem` APIs do not expose a file-attachment collection or attachment add, remove or content-fetch methods. This finding is based on Apple's documented public members and the installed macOS SDK's public `EKEvent.h` and `EKCalendarItem.h`, inspected without opening an EventKit store. Notes and an event URL are exposed, but neither establishes a native file attachment. Apple's Calendar application having additional functionality does not establish a public EventKit API. See Apple's [EKEvent](https://developer.apple.com/documentation/eventkit/ekevent), [EKCalendarItem](https://developer.apple.com/documentation/eventkit/ekcalendaritem) and [event URL](https://developer.apple.com/documentation/eventkit/ekcalendaritem/url) documentation.

The current backend therefore cannot reliably list native attachment metadata, add a file to an event, or fetch its bytes. An empty list would falsely imply that the event has no attachments; unsupported or unknown must remain distinct from a verified empty result. Private selectors, private Calendar databases and copying local attachment caches are outside this design. Existing event reads, fingerprints and retained recovery snapshots do not inventory native attachments or establish their preservation/restoration.

## Two possible directions

| Direction | What it would provide | Work and limits still unresolved |
| --- | --- | --- |
| Investigate a supported provider API for native attachments | Files attached to provider events and, where supported, visible in Calendar and other clients. | Identify the intended account/provider, documented attachment capabilities, separate scoped authentication, event/occurrence identity mapping, concurrency control, provider limits and cross-client synchronization. No provider support or authorization has been established. |
| Explicitly MCP-only file associations | Protected files associated with an opaque event reference in this integration, with metadata listing and a separate content fetch. | Requires the user's acceptance that files are local integration data: they are not native Calendar attachments and do not automatically synchronize to Calendar, iCloud or other clients. Storage lifetime, event deletion/move behavior and recovery semantics need a reviewed design. |

The iCalendar format defines [`ATTACH` in RFC 5545 §3.8.1.1](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.1.1); [RFC 8607](https://www.rfc-editor.org/rfc/rfc8607.html) describes CalDAV managed attachments and capability discovery. These documents establish protocol possibilities, not support by the user's provider, availability through EventKit, or permission to access account credentials. A provider route would introduce a new trust and authentication boundary; it cannot silently reuse macOS Calendar access as provider authorization.

## Planned read contract

Both directions must follow the user's requested separation: **ordinary event reads and attachment listings return metadata only; an explicit separate MCP tool retrieves file content.** The following fields are design requirements, not published schemas. The current thirteen tools have no attachment fields or attachment operations; native attachment presence remains unknown.

An attachment-list operation would accept a previously resolved opaque event/occurrence ID and return bounded, paginated metadata. Each entry would identify its source (`native_provider` or `mcp_only`), opaque attachment ID, display filename, declared media type, byte size and content digest/version when reliably known. Unknown values must be explicit. A capability/completeness status must distinguish unsupported enumeration, partial results and a verified complete empty list. Metadata must not contain bytes, base64, extracted text, local paths, provider credentials or temporary signed download URLs. Listing must not fetch or parse attachment bodies to enrich metadata.

A separate content-fetch operation would accept the event ID and an attachment ID returned for that event, optionally bound to the listed content version. It must resolve the attachment again in the authorized source, verify event association and current access, enforce limits and reject stale or ambiguous identity. It must never accept an arbitrary URL or filesystem path as an attachment identifier. Content is returned only for this explicit call, with its actual byte count, digest, media type and source. File content and filenames are untrusted data; fetching does not authorize executing, opening active content or following links in a file.

MCP permits binary content as a base64 `blob` in an embedded resource and supports separate `resources/read` requests. See the official [tool results](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) and [resources](https://modelcontextprotocol.io/specification/2025-11-25/server/resources) specifications. This project's current protocol advertises tools only and serializes native results as text plus structured JSON; it implements neither resource methods nor a binary-result mapper. A future implementation must choose and test the output contract through HTTP, stdio and the actual ChatGPT host. Protocol validity alone does not establish downloadable-file presentation or automatic PDF/image ingestion by ChatGPT.

## Future ingest and write requirements

ChatGPT documents top-level tool file inputs using `_meta["openai/fileParams"]`. The file-object schema declares `download_url`, `file_id`, `mime_type` and `file_name`, requiring only the first two inside the object. Actual file input behavior through this private custom-MCP tunnel remains unverified. See the official OpenAI [file-input contract](https://developers.openai.com/plugins/reference#define-file-inputs). A host file reference is an ingress reference, not an existing calendar attachment or proof of file content.

Before implementing either direction, the reviewed design must specify:

- **Bounded ingress and storage.** Receive user-selected bytes through a protected boundary, compute the digest and size locally, then issue an opaque immutable staged-file reference. Do not accept unrestricted local paths, `file:` URLs or arbitrary remote URL fetches. Any approved download mechanism needs strict destination rules, address validation/pinning against private/link-local/loopback targets and DNS rebinding, redirect rejection or equivalent validation at every hop, TLS validation, no credential forwarding, bounded duration and streamed byte limits. Temporary signed URLs and provider secrets must not enter previews, history or logs. Raw base64 ingress, if selected instead, also requires strict decoded-size and canonical-encoding checks.
- **Explicit numeric limits.** Select per-file, file-count, per-event, total-storage, response and temporary-storage limits before publishing tools. Current transport limits are 1 MiB requests, 4 MiB native responses and 8 MiB HTTP responses; base64 expansion and duplicated text/structured output reduce usable capacity. Do not raise existing limits without a resource-budget review. Expired staging and interrupted uploads require safe cleanup; no automatic decompression or content execution is needed.
- **Identity and stale checks.** Bind staged bytes to the selected installation/account, source, target calendar, event and occurrence. Filenames and MIME labels are claims, not identity. Native/provider IDs require verified mapping; recurrence, detached occurrences, moves, deletes, external replacement and concurrent attachment edits must fail closed when ambiguous. Recheck both the event and attachment inventory/version immediately before writing.
- **Exact preview and execution.** The native broker must sign the precise addition/removal/replacement, source, filename, media type, byte size and digest, alongside the complete relevant before/after inventory and target. Provider attachment changes can notify invitees; the preview must also cover recipient, sharing and scheduling effects described in [RFC 8607 §3.12.6](https://www.rfc-editor.org/rfc/rfc8607.html#section-3.12.6). Reassess the current `openWorldHint: false` if the feature uploads or shares files with attendees or other provider recipients. Keep binary content outside the human-readable preview, bound immutably by digest. Commit accepts the complete authenticated preview only; transport cannot substitute bytes or targets. ChatGPT native confirmation remains the normal write-consent surface, with no caller approval boolean or pending approval workflow.
- **Journal, audit and uncertainty.** Persist the immutable execution payload, nonce claim and durable audit intent before any association or provider mutation. Retain required content under protected storage until execution/recovery dependencies permit removal. Serialize writes, check policy and replay natively, verify the resulting association/provider state and record conservative unknown outcomes for uncertain partial uploads or linking. Multi-step provider upload and event linking are not one atomic transaction. Do not blindly retry, publish orphaned uploads, or claim visibility into host denials or other clients.
- **Retention and recovery.** Define encrypted storage, keys, expiry, staging cleanup, storage quotas, event deletion/move handling and recovery together. Ordinary event history must remain metadata-only for attachments; content retrieval stays explicit, including for retained history. Recovery must disclose whether exact bytes are retained and restorable, preserve unresolved intent and replay/quota history, and reject unavailable content rather than claim complete restoration. Audit purge, file cleanup, migrations and backup restore must preserve authoritative execution evidence. Do not rewrite legacy fingerprints or claim native attachment recovery from old snapshots.
- **Verification and release.** Use synthetic files/providers for metadata-only boundaries, cross-event ID rejection, stale content, malformed/oversized input, tampering, replay, denied access, interrupted execution, expiry and recovery. Verify actual host file-reference/binary behavior with harmless fixtures before advertising it. Any provider connection, Calendar permission prompt or live calendar write remains a separately scoped user step; this unattended follow-up authorizes none.

No implementation direction, numeric limits, new authentication or final tool schema has been selected. The existing thirteen tools and deployed service behavior remain the current contract.
